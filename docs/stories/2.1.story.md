# STORY-2.1: Endurecer a governança dos hooks — autoridade real, detecção robusta e gate da story entregue

**Status:** Ready
**Épico:** 2 — Release v0.3 (correções do uso real)
**Criada em:** 2026-11-18
**Score de validação:** 9/10

## Por quê (contexto de negócio)

A revisão dos hooks da v0.2, com testes reais (exit 0 onde deveria ser 2), mostrou que a governança determinística das Constituições Art. II (push só do shipper / CON-1 / FR-4) e Art. III (gate antes de ship / FR-6) **pode ser contornada sem esforço**: push via PowerShell não passa por hook nenhum; qualquer agente se autoriza escrevendo `FORGE_ACTIVE_AGENT=shipper` em qualquer posição do comando; variações comuns de invocação do git escapam da regex; e o gate-enforcer libera qualquer push porque as stories 1.1–1.3 já estão Done/PASS. O PRD §9 prevê "correções do uso real" na v0.3, e o piloto em projeto de cliente (FR-9) não deve começar com a governança furada.

## O quê (escopo)

1. **Matcher** `Bash|PowerShell` em `hooks/hooks.json`. O ambiente do Helder é Windows, com a ferramenta PowerShell como shell principal.
2. **Módulo compartilhado** `hooks/_shared.cjs` (Node stdlib): detecção de push/PR, verificação de autoridade e leitura do override. Os dois hooks passam a usá-lo, o que acaba com a duplicação atual (`push-authority.cjs:19-25` e `gate-enforcer.cjs:30-31,44-46`).
3. **Autoridade pelo payload, não pelo texto do comando:** o campo `agent_type` do payload PreToolUse identifica o shipper. O prefixo `FORGE_ACTIVE_AGENT=shipper` no comando e a variável `process.env.FORGE_ACTIVE_AGENT` **deixam de autorizar** (ver Decisões D-A/D-B).
4. **Detecção endurecida:** cobre opções globais do git com valor (`-C <path>`, `-c k=v`, `--git-dir=…`, `--git-dir <path>`), executável com caminho e/ou `.exe` (inclusive entre aspas e com o operador `&` do PowerShell), `gh pr create|merge` e `gh api` em endpoints que criam ou fazem merge de PR. A detecção também passa a evitar falso positivo em subcomandos legítimos como `git stash push`.
5. **Gate pela story da entrega atual:** o gate-enforcer extrai `[STORY-x.y]` do assunto do commit HEAD e valida **essa** story, não "qualquer uma".
6. **Veredito ancorado:** o PASS/CONCERNS só conta na linha `Veredito:`, no formato que as stories 1.1–1.3 já usam.
7. **Testes versionados** `scripts/test-hooks.cjs`, com tabela de casos e exit 0/2 esperado por caso. Inclui os casos do script de revisão.
8. **Docs mínimas** que descrevem o sinal de autoridade, porque ficariam falsas: `agents/shipper.md:19`, `skills/sdc/SKILL.md:18`, `skills/onboarding/SKILL.md:61`, `docs/architecture.md:59,61` + nova decisão D-7. Também o formato do veredito em `skills/gate/SKILL.md:12`.

**NÃO está no escopo:**
- Reordenação de commits no `/sdc`; separação de arquivos internos vs. distribuídos ao cliente; `docs/economia.md`; inconsistências de README/MEMORY/versão. Essas são outras stories.
- Fechar **todo** vetor de contorno. Ficam como risco residual documentado, não implementado: alias do git (`git p` com `alias.p=push`), indireção por variável (`$g push`, `Start-Process git -ArgumentList push`), push executado por script em arquivo (`node deploy.cjs`), chamada HTTP direta à API do GitHub (`curl`/`Invoke-RestMethod`). O hook é guard-rail determinístico de texto, não sandbox.
- Validar mais de um commit do push (só o HEAD, ver D-C) e push de refs que não sejam o HEAD (`git push origin outra-branch`, tags).
- Bloquear commit local ou alterar o fluxo do builder/reviewer.

## Decisões tomadas nesta story (confirmar com o Helder)

- **D-A — Autoridade = `agent_type`.** O shipper é reconhecido por `data.agent_type` igual ao valor que a T-1 observar para o subagent do plugin (esperado `forge360:shipper`). O nome sem namespace (`shipper`) só é aceito se a T-1 mostrar que é assim que o plugin o reporta: aceitar `shipper` sem necessidade abriria o push para qualquer agente de projeto chamado "shipper". Sem `agent_type` (sessão principal) → bloqueia. Isso é coerente com o Art. II ("nem o principal contorna").
- **D-B — Prefixo de env removido como sinal de autoridade.** No modo `agent_type`, `FORGE_ACTIVE_AGENT=shipper` no comando é **ignorado**: não autoriza e não bloqueia. O shipper pode continuar escrevendo o prefixo sem efeito, o que mantém compatibilidade de hábito. `process.env.FORGE_ACTIVE_AGENT` também deixa de autorizar: ligado no lançamento da sessão, tornaria toda a sessão (principal incluída) capaz de push. Isso substitui a D-5 de `architecture.md:76`.
- **D-B' — Fallback, se a T-1 provar que a versão instalada NÃO envia `agent_type` em subagent:** o modo prefixo estrito passa a valer. O comando precisa **começar** com `FORGE_ACTIVE_AGENT=shipper ` imediatamente seguido da invocação git/gh, e não pode conter separadores de comando (`;`, `&&`, `||`, `|`, quebra de linha, `` ` ``, `$(`). Isso mata `echo … ; push` e `export …; push`, mas continua forjável por quem escrever o prefixo correto. Registrar como risco residual e o reviewer dá no máximo CONCERNS. Em PowerShell o prefixo não é sintaxe válida, então no fallback o push via PowerShell fica **bloqueado** e o shipper usa a ferramenta Bash.
- **D-C — Story da entrega = IDs `[STORY-x.y]` no assunto do HEAD** (`git log -1 --format=%s`). Justificativa determinística: convenção do builder (`agents/builder.md:20`, `CLAUDE.md:25`) + Modelo 1 / "commit único" do shipper (`agents/shipper.md:18`). Com vários IDs no assunto, **todos** precisam passar. HEAD sem ID → **bloqueia** com mensagem clara; `FORGE_GATE_OVERRIDE=1` continua valendo.
- **D-D — Módulo compartilhado `hooks/_shared.cjs`** (um arquivo, sem subpasta). O prefixo `_` sinaliza que não é hook registrado. Over-engineering evitado: só três funções exportadas.
- **D-E — Numeração:** Épico 2 = release v0.3. A story vem antes do épico do piloto FR-9 porque o piloto depende de governança correta.

**Payload do hook (doc oficial `code.claude.com/docs/en/hooks`, consultada em 2026-11-18):** campos comuns `session_id`, `cwd`, `hook_event_name`, … Também `agent_id` e `agent_type`, este último "presente quando a sessão usa `--agent` ou o hook dispara dentro de um subagent; para subagents, o tipo do subagent tem precedência". O formato exato do valor para agente de plugin (com ou sem `forge360:`) e o `tool_input` da ferramenta PowerShell (presume-se `command`) **não estão documentados**, por isso a T-1 é obrigatória.

**Contrato sugerido de `hooks/_shared.cjs`** (CommonJS, `'use strict'`, só stdlib):
- `detectar(cmd)` → `{ tipo: 'push'|'pr'|null, gitC: string|null }`. Abordagem recomendada: regex com
  - fronteira à esquerda `(^|[\s;&|(`'"])`;
  - executável `(?:(?:"[^"]*[\\/])|(?:'[^']*[\\/])|(?:[^\s"';&|]*[\\/]))?git(?:\.exe)?["']?`, sem distinção de maiúsculas no nome do executável;
  - zero ou mais opções globais: `-C`/`-c`/`--git-dir`/`--work-tree`/`--namespace`/`--config-env` com valor separado (aspas duplas, simples ou token), `--opt` ou `--opt=valor`, e flags curtas `-[A-Za-z]`;
  - por fim o subcomando **exatamente** `push` (`\s+push\b`).

  Como o subcomando é o primeiro token não-opção, `git stash push` e `git commit -m "… push"` ficam de fora. Para PR: `gh(?:\.exe)?\s+pr\s+(create|merge)\b`, ou `gh api` com `pulls/\d+/merge`, ou `gh api` com `/pulls` + (`-X|--method` `POST|PUT` ou campo `-f|-F|--field|--raw-field|--input`). Capturar o valor de `-C` para o AC-13.
- `ehShipper(data)` → boolean, conforme D-A (ou D-B' se a T-1 mandar).
- `override(cmd)` → boolean (forma de texto + `process.env.FORGE_GATE_OVERRIDE === '1'`).
- Os hooks fazem `require(path.join(__dirname, '_shared.cjs'))`. Se o `require` lançar, o Node sai com código 1, que no Claude Code é não-bloqueante (fail-open). Isso é aceitável pelo padrão de tolerância, porque o `test-hooks.cjs` pega a quebra antes da entrega.

**Gate (gate-enforcer):**
- Base = `gitC` resolvido contra `data.cwd || process.cwd()`, ou o próprio cwd.
- `execFileSync('git', ['-C', base, 'log', '-1', '--format=%s'], { encoding: 'utf8', stdio: ['ignore','pipe','pipe'], timeout: 3000 })` com array de argumentos, sem shell. Se falhar → AC-12 (exit 0 + aviso).
- IDs: `/\[STORY-(\d+\.\d+)\]/g` → arquivo `docs/stories/{x.y}.story.md`. Status por regex `gate-enforcer.cjs:70` (manter).
- Ordem: override → autoridade (não-shipper → exit 0) → `docs/stories/` existe? → HEAD → validar cada ID.

**Padrões a seguir:**
- `architecture.md:58-61`: stdin JSON → decide → exit 0/2 + stderr; tolerante a payload ilegível; rápido no caminho feliz. O `git log` só roda depois de detectado push autorizado, então o NFR-5 não é afetado.
- NFR-1 (zero deps, Node ≥ 18); NFR-2 (mensagens em pt-BR); CON-1 (push/PR só do shipper).
- Estilo do código: o de `gate-enforcer.cjs` (comentários citando AC/artigo, CommonJS, `'use strict'`).
- `CLAUDE.md:36-38`: comandos e código de teste sem o literal do push. Payloads gerados em JS e passados por `spawnSync(..., { input })`.
- Fixtures do teste em `os.tmpdir()` (`fs.mkdtempSync`), com `git init` + commit criados por `execFileSync('git', ['-c','user.name=t','-c','user.email=t@t', 'commit', '--allow-empty', '-m', '…'])`. Limpar ao final. Nunca usar o repo real como fixture do gate, porque o HEAD dele muda.
